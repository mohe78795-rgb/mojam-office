# تحديث زوع: اللهجة اليمنية ومسودات طلبات العملاء

## ما الذي يضيفه التحديث؟

1. يحسن تعليمات Gemini لتكون اللهجة اليمنية البيضاء أقرب للطبيعية عند اختيار أحد الإعدادين `yemeni_neutral` أو `yemeni_short`، مع تجنب خلط اللهجات أو المبالغة. عند اختيار الفصحى/أسلوب آخر لا يفرض تعليمات اللهجة اليمنية.
2. يضيف زر **تحليل الطلب كمسودة** في محادثة SMS. يحلل الرسالة الواردة المحددة إلى صنف وكمية ووحدة بيع، ويدعم التمييز بين **شبك** و**بالحبة**.
3. لا يحول بين الشبك والحبات، ولا يخمن الصنف أو الكمية. إذا نقصت معلومة، يحفظ الحالة `needs_clarification` ويعرض سؤالاً توضيحياً مقترحاً.
4. يضيف زر **مسودات الطلبات** وقائمة مراجعة، بالإضافة إلى مساري API:
   - `POST /api/orders/drafts`: تحليل وحفظ مسودة؛ يتطلب جلسة مستخدم.
   - `GET /api/orders/drafts?status=open&limit=50`: عرض المسودات للمراجعة؛ يتطلب جلسة مستخدم.
5. يحفظ المسودات في MongoDB داخل `order_drafts` مع فهارس للرسائل المصدر وقائمة المراجعة. يعيد تحليل الرسالة نفسها المسودة السابقة بدلاً من إنشاء نسخة مكررة عند توفر معرف الرسالة.

## ما لا يفعله التحديث

- لا يؤكد الطلب ولا يحجز المخزون ولا ينشئ فاتورة.
- لا يرسل سؤال التوضيح ولا أي رسالة جديدة للعميل.
- لا ينشئ تهاني أو تذكيرات أو حملات استباقية. لا تتغير إعدادات الإرسال التلقائي الحالية.
- لا يحتاج تعديلات Android/Java أو إعادة بناء APK؛ الميزة ضمن واجهة الويب والخادم فقط.

المراجعة في هذه المرحلة **عرض للمسودة فقط**. أي خطوة لاحقة لتأكيد الطلب/حجزه تحتاج تعريف قواعد المخزون والوحدة وموافقة الموظف صراحةً.

## الملفات في هذه الحزمة

من جذر المستودع، تستبدل الملفات التالية:

```text
server/src/server.js
server/src/gemini.js
public/index.html
public/order-drafts.js
```

بقية الملفات لا تتغير. يفترض أن يحتوي مشروعك مسبقاً على وحدة `server/src/business-context.js` و`server/src/invoice-numbering.js` من تحديث الربط السابق.

## التثبيت من Termux

انتقل أولاً إلى جذر المستودع الذي يحتوي مجلدي `public` و`server`. إذا كنت داخل هذا المجلد بالفعل فلا تنفذ `cd`:

```bash
pwd
test -d public && test -d server || { echo 'المجلد الحالي ليس جذر المستودع؛ انتقل إلى المجلد الذي يحتوي public وserver.'; exit 1; }
unzip -o "$HOME/storage/downloads/mojam_zoe_yemeni_order_drafts_patch.zip" -d .
node --check server/src/server.js
node --check server/src/gemini.js
node --check public/order-drafts.js
git diff --check
```

راجع الملفات المتغيرة، ثم ارفع التعديل:

```bash
git status --short
git add server/src/server.js server/src/gemini.js public/index.html public/order-drafts.js README_ZOE_YEMENI_ORDER_DRAFTS_AR.md
git diff --cached --check || exit 1
git commit -m "Add Yemeni order draft analysis"
git push origin main
```

لا تضف أي ملف `.env` ولا ترفع أسرار MongoDB أو Gemini. عند اتصال GitHub بخدمة Render يبدأ النشر بعد الدفع؛ انتظر نجاح Deploy قبل الاختبار.

## الاختبار بعد النشر

1. افتح التطبيق وسجل الدخول، ثم افتح محادثة عميل وبها رسالة واردة.
2. اضغط **تحليل الطلب كمسودة**.
3. راجع الصنف والكمية والوحدة في النافذة. مثال متوقع: «أريد 3 شبك كبير» ← `3 شبك — كبير`.
4. مثال آخر: «أريد 12 حبة وسط» ← `12 بالحبة — وسط`.
5. عند نقص المعلومات تظهر حالة **تحتاج توضيحاً** وسؤال مقترح. لا يُرسل السؤال تلقائياً.
6. اضغط **مسودات الطلبات** لإعادة عرض المسودات المفتوحة.

المسودة مرتبطة برقم الهاتف الذي طابقه التطبيق، وتظهر في MongoDB ضمن `order_drafts`. لاختبار API يدوياً، ضع access token في متغير طرفي محلي ولا تشاركه:

```bash
BASE_URL='https://mojam-office.onrender.com'
read -rsp 'Access token: ' TOKEN; echo
curl -sS "$BASE_URL/api/orders/drafts?status=open&limit=50" \
  -H "Authorization: Bearer $TOKEN"
unset TOKEN
```
