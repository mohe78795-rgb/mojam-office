# إصلاح عاجل لتكرار رسائل SMS

## أوقف الإرسال الآن

1. في الهاتف افتح **الإعدادات → التطبيقات → تطبيقك → فرض الإيقاف**. لا تكتفِ بإغلاق الشاشة أو تصغير التطبيق.
2. اترك التطبيق متوقفاً إلى أن تنشر إصلاح الخادم وتبني APK جديداً. الإيقاف القسري يوقف عامل الخلفية والواجهة القديمة؛ الرسائل التي أُرسلت بالفعل لا يمكن سحبها.
3. لا تعد تفعيل **الإرسال التلقائي** قبل انتهاء الخطوات والاختبار برسالة واحدة إلى رقم تملكه.

## سبب الخطر الذي عثرنا عليه

كان عامل Java يستدعي `/api/sms/native/outbox/next` حتى خمس مرات بعد كل SMS واردة، وكان هذا المسار يسحب أقدم الردود من طابور عام، لا الرد المرتبط بالرسالة الحالية. لذلك قد يرسل عامل واحد ردوداً متراكمة لعملاء مختلفين. كما كان استدعاء `onNativeSmsReceived` في نسخة الواجهة القديمة قادراً على توليد/إرسال رد ثانٍ محلياً إذا لم تصل حالة الخادم في الوقت المناسب. وعند خطأ حصة Gemini 429 كان الرد الاحتياطي يُنشأ لكل رسالة واردة.

## ما يفعله الإصلاح

- عند تشغيل نسخة الخادم بعد التحديث، يوقف `autoSend` **مرة واحدة** ويحوّل الردود القديمة `queued` إلى `draft` حتى يراجعها الموظف.
- يجعل `/api/sms/native/outbox/next` يفشل بشكل آمن: لا يسلم أي رسالة قديمة، ويحوّل الطابور المتبقي إلى مسودات.
- يرجع الخادم للـJava ردّاً مباشراً واحداً مربوطاً برسالة SMS الواردة نفسها. نسخة Java المرفقة لا تسحب طابوراً عاماً؛ ترسل هذا الرد الواحد فقط.
- إذا رد Gemini بـ429، يوقف الخادم `autoSend` تلقائياً ويحوّل الردود المتراكمة إلى مسودات. لا يرسل الرد الاحتياطي في تلك الحالة.
- تمنع الواجهة الجديدة توليد مسار محلي موازٍ في تطبيق Android.

## تطبيق إصلاح الخادم عبر Termux

نزّل `mojam_sms_duplicate_hotfix.zip` إلى مجلد Downloads. من Termux، حتى لو كنت داخل `server/scripts`، نفّذ:

```bash
set -eu
ZIP="$HOME/storage/downloads/mojam_sms_duplicate_hotfix.zip"
ROOT="$(git rev-parse --show-toplevel)"
cd "$ROOT"
test -d public && test -d server
test -f "$ZIP"
unzip -o "$ZIP" -d .
node --check server/src/server.js
node --check public/index.html
git diff --check
git add server/src/server.js public/index.html README_SMS_DUPLICATION_HOTFIX_AR.md
git diff --cached --check
git commit -m "Stop duplicate native SMS dispatch"
git push origin main
```

انتظر نجاح Deploy في Render. عند بدء الخادم، سيُوقف الإرسال التلقائي مرة واحدة ويحوّل الطابور القديم إلى مسودات. لا ترفع ملفات `.env` أو مفاتيح Gemini/MongoDB. مجلد `android-java/` في ZIP مصدر لنسخ Android فقط؛ لا تضفه إلى مستودع السيرفر.

## تحديث APK — مطلوب قبل استئناف الإرسال

تطبيقك يفتح `https://app.local/index.html` في WebView؛ لذلك لا يكفي نشر `public/index.html` على Render لتحديث نسخة الواجهة المضمنة داخل APK.

1. في مشروع Android Studio استبدل `SmsAutoReplyJob.java` في مسار الحزمة `com/Yaaqoub/Market/Card/` بالملف الموجود في `android-java/SmsAutoReplyJob.java` داخل ZIP.
2. انسخ `public/index.html` المحدّث إلى مصدر صفحة WebView المحلية التي تُقدَّم باسم `https://app.local/index.html` (راجع إعدادات `WebViewAssetLoader`/Gradle في مشروعك؛ قد يكون مصدرها `app/src/main/assets/index.html`).
3. ابنِ APK جديداً وثبّته، لكن اترك الإرسال التلقائي متوقفاً.

## تحقق آمن

- تأكد من نجاح نشر Render وتشغيل التطبيق الجديد.
- اترك الإرسال التلقائي متوقفاً، وراقب المحادثة والطابور.
- بعد ذلك، إن أردت استئنافه، فعّله يدوياً لرسالة واحدة إلى رقم تملكه. لا تفعّله على جميع العملاء حتى تتأكد من وصول رد واحد فقط.
- إذا لم تستطع بناء APK الجديد الآن، أبقِ التطبيق قسرياً متوقفاً والإرسال التلقائي معطلاً.

إيقاف العامل لا يحذف سجل المحادثات ولا الرسائل؛ الردود التي لم تُرسل تتحول إلى `draft` للمراجعة. حالة `submitted` تعني أن `SmsManager` قبل الإرسال، ولا تثبت التسليم النهائي.
